# 网页版测试手册：12 项需求怎么测、怎么看通过/失败

> 适用：`F:\c\12\newweb` 网页控制台（双击 `start.bat` 后访问 http://127.0.0.1:8090）

## 先搞懂一个关键概念：两种"结果"

网页上有两套独立的操作，**它们的状态互不相通**，混用就会觉得"结果不对"：

| 操作区 | 状态 | 适用 |
|---|---|---|
| **试验台页** | 一个长期存在的 ECU/总线/信号，你一步步点，实时看信号变化 | 单步演示、手动调参 |
| **脚本执行页** | 每次点"运行"都用**全新状态**从头跑一遍脚本，跑完销毁 | 自动化回归、批量验证 |

所以：**你在试验台注入的故障，不会带到脚本执行里**；反过来脚本跑完，试验台的信号也不会变。

## 一、6 个必做功能的测试方法

### 1. 虚拟 ECU（状态机 + 周期任务 + ≥8 信号）

**试验台页**：
1. 点 `POWER ON`，看顶部"ECU 状态"从 POWER_OFF → INIT
2. 连续点 `WAIT 100`（或一次 WAIT 300），观察状态链依次走亮：`INIT → SELF_TEST → STANDBY → RUN`
3. RUN 状态下，看"信号"表里 `engine_speed`、`vehicle_speed`、`oil_pressure` 随油门自动变化 → 这是**周期任务**在跑
4. 数一下信号表行数：≥8 路（实际 12 路，含 ecu_state、ecu_fault_latched 两路状态镜像）

**怎么算通过**：状态链按顺序走到 RUN，信号自动刷新，信号数 ≥8。

### 2. 虚拟总线（帧队列 / 丢失 / 延迟 / 篡改）

**试验台页 → 虚拟总线**：
1. 先把 `丢失率` 设 0、`延迟` 设 0、`篡改` 关，点 `应用`，然后 `WAIT 1000` → 看"已发布/已交付"两者相等，丢 0
2. 把 `丢失率` 设 30，`应用`，`WAIT 1000` → 看"已丢失"明显 > 0
3. 把 `延迟` 设 50ms，`应用`，`WAIT 1000` → 看"队列深度"出现非 0（帧在排队）
4. 把 `篡改` 开，`应用`，`WAIT 1000` → 看"已篡改" > 0

**怎么算通过**：四个计数器（发布/交付/丢失/篡改）随参数变化符合预期。

### 3. 测试脚本（设置/等待/故障/断言/复位）

**脚本执行页**：
1. 点 `载入示例`，点 `运行脚本`，看右侧"执行结果"表格每个步骤的 PASS/FAIL
2. 命令对应：SET=设置、WAIT=等待、FAULT=故障、ASSERT=断言、RESET=复位、POWER=电源

**怎么算通过**：每个步骤都有明确 PASS/FAIL，顶部汇总显示"步骤/通过/失败"。

### 4. 数据记录（CSV + 按时间/信号查询）

**数据记录页**：
1. 选信号 `engine_speed`，起始 0、结束 100000，点 `查询` → 表格列出 (时间, 值) 点对
2. 后端同时把数据写进 `F:\c\12\newweb\data\out\run.csv`，用 Excel 打开能看到完整时间序列

**怎么算通过**：查询返回多条带时间戳的记录，CSV 文件存在且列是 `timestamp,signal1,signal2,...`。

### 5. 报告（用例级 + 步骤级）

**报告页**：点 `读取最近一次报告`，看到汇总 + 每个步骤一行（用例名/行号/步骤/期望/实际/结果）。

**怎么算通过**：有"用例级"分组（case 列）和"步骤级"明细（每个 step 一行）。

### 6. 统一配置 / 错误码 / 日志 / 构建

- **配置**：`virtual_hil/examples/default_config.ini`（tick、ECU 超时、总线参数等）
- **错误码**：`virtual_hil/include/hil_common.h` 的 `hil_status_t`
- **日志**：后端运行窗口会打印 `[INFO]/[WARN]/[ERROR] [模块] 内容`
- **构建**：`make` / `start.bat` / `start.ps1` 一键编译

**怎么算通过**：`start.bat` 能一键编译并启动；后端窗口有日志输出。

## 二、6 个必测场景的测试方法

### 1. 正常上电和完整业务流程

脚本执行页 `载入完整套件` → 运行 → 第一个用例 `power_off_and_restart` 里，`ASSERT ecu_state EQ RUN` 通过。

### 2. 启动/通信超时及断电

试验台页：
- **断电**：`POWER OFF` → 状态变 POWER_OFF，`engine_speed` 归 0（安全输出）
- **上电**：`POWER ON` → 重新走 INIT→...→RUN
- **通信超时**：`FAULT ECU COMM` → 状态变 FAULT（可恢复）

### 3. 信号边界、传感器断线

试验台页：
- **边界**：`SET engine_speed 0` 和 `SET engine_speed 8000`，看信号表值正确到上下限
- **断线**：故障类型选 `OPEN_CIRCUIT`，注入 `coolant_temp` → 信号表里该信号标"开路"，值归 0

### 4. 报文丢失、延迟、篡改

同"必做功能 2"的总线测试。

### 5. 可恢复与锁存故障

试验台页（这是最容易理解"通过/失败"的地方）：
- **可恢复**：`FAULT ECU COMM` → FAULT → `FAULT ECU CLEAR` → RECOVERY → 自动回 RUN
- **锁存**：`FAULT ECU LATCH` → FAULT；然后**连点 WAIT 很久**，状态**一直停在 FAULT**（这就是"锁存"——不自愈）；只有 `FAULT ECU CLEAR` 才能回到 RECOVERY

**怎么算通过**：锁存后 WAIT 多久都不自愈；COMM 可恢复、LATCH 不可自愈，两者行为不同，这才叫"可恢复与锁存故障"。

### 6. 错误脚本、日志失败、长时间运行

脚本执行页手动写：
- **错误脚本**：写一行 `BOGUS 1` 或 `FAULT ECU LATCH`（缺参数）→ 点运行 → 返回错误，不崩溃
- **长时间运行**：`WAIT 10000` → 正常完成

## 三、重点澄清：为什么"注入故障"显示"通过"？

这是最容易误解的地方。**"故障注入成功" ≠ "测试失败"**，恰恰相反：

| 你看到的 | 真实含义 | 该不该"通过" |
|---|---|---|
| `FAULT engine_speed STUCK 1500` 步骤显示 **PASS** | 故障**注入这个动作**成功了 | 该通过（注入成功是好事） |
| `ASSERT engine_speed EQ 1500` 显示 **PASS** | 故障**真的生效了**，转速卡在 1500 | 该通过（证明故障起了作用） |
| `ASSERT engine_speed EQ 9999` 显示 **FAIL** | 期望值和实际不符 | 该失败 |

**例子**（脚本执行页可以亲手试）：

```
TEST 故障生效验证
SET throttle_position 30
WAIT 300
FAULT engine_speed STUCK 1500 100   ← 这行 PASS = 注入成功
WAIT 20
ASSERT engine_speed EQ 1500 1       ← 这行 PASS = 故障真的把转速卡在1500了
WAIT 200                            ← 超过100ms故障窗口
ASSERT engine_speed GT 800 1        ← 这行 PASS = 故障自动解除，转速恢复
END
```

如果你想让报告**显示失败**，就把断言期望写一个和实际不符的值，例如：

```
ASSERT engine_speed EQ 9999 1       ← 实际是1500，这行会 FAIL
```

这样顶部汇总就会显示"失败 1"，`all_passed = false`。

**一句话总结**：注入故障后"全部通过"，说明**故障注入和断言都正常工作**——故障注入本身就该 PASS，你要验证的是"注入后信号值变没变"，靠的是 ASSERT 那一行的期望值和实际值对不对得上，而不是 FAULT 那一行。
