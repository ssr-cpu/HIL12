## 关键结论（需求 vs 实现）

- 脚本层支持的故障：`FAULT <signal> OFFSET|STUCK|NOISE|DROPOUT|OPEN_CIRCUIT [value] [duration_ms]`，
  实现在 `src/hil_fault.c` 的 `hil_fault_manager_apply()`，每个 tick 重算（先还原 raw_value 再叠加）。
- **锁存故障缺口**：`hil_ecu_latch_fault()` / `hil_ecu_set_comm_fault()` / `hil_ecu_power_on|off()` /
  `hil_ecu_clear_fault()` 只被 `tests/test_main.c:431 test_ecu_latched_fault` 调用，
  脚本命令（hil_script.c 只解析 TEST/SET/WAIT/FAULT/ASSERT/RESET/END）和 CLI 均无法触发 ECU 级故障。
  即"可恢复与锁存故障"必测场景只在单元测试层覆盖，演示时无法用脚本一键复现。
- 总线故障（丢失/延迟/篡改）只能由 `examples/default_config.ini` 的
  bus.loss_probability_percent / bus.delay_ms / bus.tamper_enabled 静态配置，脚本运行时不能动态注入。
- 数据查询：`hil.exe query --csv <file> --signal <name> --from <ms> --to <ms>`，输出为两列 CSV。
- 报告：`build\<out>/report.md`（步骤级表格 + 汇总指标），CSV 轨迹 `run.csv`。

## 新建 Web 控制台 `F:\c\12\newweb`（案例 12 的 Web 形态）

- 架构：C17 后端（main/http/api/session/utils）**直接链接** `virtual_hil/src/*.c`（排除 main.c），
  前端原生 HTML/CSS/JS，无框架无 CDN 依赖。核心仍是 C，符合"不许用 Python/C++ 替代核心模块"。
- 默认端口 **8090**（8080 已被 `webapp/` 旧服务占用，实测会拿到旧服务的响应，排查花了时间）。
- 会话模型：`hil_web_session_t` 持有 config/time/signals/ecu/bus/faults/data_logger/report，
  另有内存环形采样缓冲 4000×32，供 `/api/history` 按时间窗查询；同时写 `data/out/run.csv`。
- REST：state / set / wait / fault / fault/clear / ecufault / power / reset / assert /
  history / script(POST) / report / config。
- 已实测：12 路信号、STUCK 生效 1500、LATCH 后 WAIT 800 仍锁在 FAULT、CLEAR→RECOVERY、
  POWER OFF/ON、ASSERT 支持状态名（EQ INIT 解析成 1）、总线 loss=25% 时 100 帧丢 25 篡改 36、
  脚本 POST 运行 18 步全 PASS、report.md 与 run.csv 正确落盘。

### 本环境踩坑（Windows + MSYS2 gcc）
- MSYS2 gcc 对 `-I..\virtual_hil\include` 这类相对路径不可靠，**用 `-IF:/c/12/...` 正斜杠绝对路径**。
- PowerShell 5.1 单引号 URL 里不能出现 `&`（保留运算符），测试脚本里 URL 必须用双引号。
- `Start-Process` 启动服务端跑冒烟测试不可靠（进程没起来/输出被吞）；改用工具自身的
  `run_in_background` 起服务，再单独发请求。
- Windows `_mkdir()` 不创建中间层级，`data/out` 要先建 `data`；已把 `web_ensure_dir()` 改成逐级创建。
- 本环境 `Remove-Item` 走 safe-delete 会 refuse fallback delete，删不掉时用 `Move-Item` 归拢再处理。
- 新代码里 `hil_signal_t` 没有 `find_by_index`，直接用 `registry->items[i].value` 遍历即可。

## "注入故障却全部通过"——是理解误区，非 bug

- 实测后端报告逻辑正确：注入 STUCK 1500 后转速=1500，写 `ASSERT engine_speed EQ 9999` 正确 FAIL、
  all_passed=false。交互式注入后信号表也正确变 1500。
- 根因是概念混淆：**"FAULT 注入"这一步 PASS 是"注入动作成功"，不等于"测试失败"**；要验证故障
  是否生效，看的是随后 ASSERT 的期望/实际是否吻合，以及信号表数值是否变化。
- 关键认知：试验台（持久 session）和脚本执行（每次全新 executor）是**两套独立状态**，互不相通。
- 改进：① 前端信号表对"被活动故障影响"的信号加黄底高亮 + "故障:TYPE"标签；② 新增"需求验收"标签页，
  把 6 必做功能 + 6 必测场景做成可点击"去验证"的清单；③ 新增 `docs/测试手册.md` 逐条写清怎么测、
  怎么看通过/失败，并专门澄清"注入故障为什么 PASS"。
