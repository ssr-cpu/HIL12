# 案例 5：ECU启动与故障状态机 - 项目需求文档

## 1. 文档信息

- 项目性质：无硬件 C 语言综合项目
- 小组人数：6 人
- 推荐周期：3～5 天
- 语言标准：ISO C17
- 构建方式：Makefile 或 CMake
- 运行平台：Linux、macOS、Windows + MinGW/WSL

## 2. 通用工程约束

- 必须采用多文件结构，公开接口放在头文件中；
- 启用 `-Wall -Wextra -Wconversion -Wshadow -Wpedantic`；
- 测试阶段启用 AddressSanitizer 和 UndefinedBehaviorSanitizer；
- 禁止 `gets`、无长度限制的字符串写入及未检查的数组访问；
- 所有动态内存、文件和其他资源都要有清晰的释放路径；
- 错误信息必须指出模块、原因和必要的上下文；
- 核心模块不得依赖大面积全局可变状态；
- Git 提交应能反映六位成员的持续贡献。

## 3. 项目目标

实现具备超时、故障锁存和恢复策略的ECU状态机，训练枚举、事件队列、状态表和安全输出。

## 4. 项目范围

### 4.1 必做功能

1. 实现POWER_OFF、INIT、SELF_TEST、STANDBY、RUN、FAULT、RECOVERY；
2. 支持进入/执行/退出动作；
3. 实现启动、Ready和通信超时；
4. 区分瞬时、可恢复和锁存故障；
5. 读取事件脚本并生成状态覆盖报告；

### 4.2 不在本期范围

- 不连接真实车辆、ECU 或采集板卡；
- 不要求图形界面，命令行即可；
- 不要求实现完整商业标准，只实现文档明确的子集；
- 不允许用 Python、C++ 替代核心 C 模块。

## 5. 建议模块

- `state_machine`
- `ecu_states`
- `event_queue`
- `fault_manager`
- `scenario_parser`
- `coverage/report`

每个模块应提供职责说明、公开 API、错误码、所有权规则及线程/重入假设。跨模块传递指针时必须说明对象由谁创建、由谁释放、有效期到何时。

## 6. 六人分工

1. 组长/架构：状态图和集成；
2. 状态引擎：表驱动或函数表；
3. 故障管理：优先级、锁存、恢复；
4. 事件队列：排序、派发、超时；
5. 场景报告：脚本和覆盖统计；
6. 测试工程：转移覆盖、异常事件、构建；

### 6.1 协作规则

- 六人均须提交实际代码、测试和文档；
- 每位成员至少维护一个 `.c/.h` 模块；
- 接口由组内评审后冻结，修改需记录原因和影响；
- 合并前必须由非作者完成代码评审；
- 集成问题由相关模块责任人共同定位。

## 7. 输入、输出与错误处理

- 输入可来自配置文件、脚本、CSV、二进制文件或命令行；
- 文件格式必须在 `docs/file_format.md` 中定义并给出示例；
- 所有输入须检查长度、范围、格式和重复项；
- 输出至少包含正常结果、错误信息和可追踪日志；
- 程序退出码：0 表示成功，非 0 表示失败；
- 文件打开、内存分配和解析失败均不得导致资源泄漏；
- 不可信长度参与分配或地址计算前必须检查溢出。

## 8. 必测场景

1. 正常启动到RUN；
2. 各阶段断电和超时；
3. 自检失败、通信丢失；
4. 瞬时故障恢复、锁存故障复位；
5. 同一时刻多个事件、未知事件；

测试至少分为正常、边界、异常、故障注入和长时间运行五类。每个缺陷修复后必须增加回归测试。

## 9. 里程碑

| 阶段 | 主要任务 | 交付物 |
|---|---|---|
| M1 需求评审 | 澄清范围、术语和验收条件 | 需求追踪表、风险清单 |
| M2 架构设计 | 模块、接口、数据结构、文件格式 | design.md、接口头文件草案 |
| M3 模块开发 | 六人并行开发与单元测试 | 可独立测试的模块 |
| M4 集成联调 | 主流程、错误路径、日志 | Alpha 版本、联调记录 |
| M5 系统测试 | 边界、故障、压力、Sanitizer | 测试报告、缺陷清单 |
| M6 发布答辩 | 修复、文档、演示 | Release 版本、答辩材料 |

## 10. 验收标准

1. 断电始终进入安全状态；
2. 未定义事件不破坏状态；
3. 全部合法转移至少测试一次；
4. 状态日志含时间、旧状态、事件、新状态；

此外必须满足：

- 一条命令完成构建，一条命令执行全部测试；
- Debug 构建无编译警告；
- 正常退出及错误退出均无已知资源泄漏；
- README 中的步骤可在干净环境复现；
- 六位成员均能说明整体架构、接口和本人贡献。

## 11. 最终交付物

1. `src/`、`include/` 下的完整 C 源码；
2. Makefile 或 CMakeLists.txt；
3. README 与运行示例；
4. 需求追踪矩阵；
5. 架构、接口、数据结构和文件格式文档；
6. 单元测试、集成测试和端到端测试；
7. 测试数据、预期结果与测试报告；
8. Sanitizer 执行结果；
9. Git 贡献记录和代码评审记录；
10. 10～15 分钟演示及项目复盘。

## 12. 教师答辩检查点

- 为什么采用当前数据结构和模块边界？
- 指针参数的所有权与生命周期是什么？
- 最危险的越界、泄漏或整数溢出位置在哪里？
- 输入损坏时程序如何进入可控失败状态？
- 如何证明核心功能满足需求？
- 哪些测试由本人编写，曾发现什么缺陷？
- 若替换成真实硬件接口，哪些模块保持不变？
